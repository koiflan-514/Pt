# Pt 与其他 GUI 工具包

[English](../comparison.md) | 简体中文

这是 Pt 1.0 与 GTK 4、Qt Quick、Slint、egui、LVGL 和 Nuklear 的定性比较。
本文从 Linux/Wayland 上 C 应用的视角撰写，这类应用希望获得原生外观的窗口、
较小的绑定表面，以及在 C、C++、Python 或 Java 中的所有权。

本文不声称进行跨工具包基准测试。不同工具包做出不同权衡，
通常也在不同工作负载上测量；[performance.md](../performance.md) 中的数字仅描述 Pt。

## Pt 的不同之处

### 1. C ABI 就是产品

Pt 的稳定单元是一套扁平 C ABI：不透明句柄、值形态的枚举、打包颜色整数，
以及带 `void *user_data` 的 C 函数指针。C++、Python 和 Java 不通过桥接
封装 C++ 对象模型；它们直接调用相同的符号。这使绑定层很小
（整个 Python 绑定是一个文件，Java 是一个类），并让生命周期规则在各语言间保持一致。

GTK 也有 C 核心和内省，但其绑定继承 GObject 约定和大得多的 API 表面。
Qt 的天然归宿是 C++；Python 支持良好，但 Java 不是官方一等目标。
Nuklear 也是 C ABI，但它是立即模式且与渲染器无关。

### 2. Wayland 是平台，而不是一个后端

Pt 直接实现 `xdg-shell`（包括 `xdg_popup`）、`xdg-decoration`、
`fractional-scale-v1`、`viewporter`、`text-input-v3`、`wl_data_device`、
`pointer-gestures-v1`、`tablet-v2`、客户端标题栏和 `wl_shm`。
没有 X11 回退、没有 Win32 层，也没有需要配置的 GL 上下文。
客户端装饰由 Pt 绘制，这在 niri 和 wlroots 配置等平铺合成器上很重要。

Qt 和 GTK 支持许多平台，因此带有平台抽象层。这对它们是正确的选择；
Pt 有意用可移植性换取小型、可预测的 Linux 桌面栈。

### 3. 按需帧的软件渲染

Pt 的渲染器基于这样的前提：GUI 工作大多是平面表面、边框、圆角卡片和文本。
它绘制到共享内存缓冲区，并仅在状态变化时提交。损坏会累积到一个由合并瓦片
组成的小索引中，每个瓦片在持久后备画布上于各自裁剪区内重绘，
并作为 `wl_surface.damage_buffer` 提交，因此一次局部更新成本约为完整密集窗口重绘的 7%，
并遍历可见树的四分之一。布局失效会记录脏子树，并在安全时从其固定祖先重新布局。
长数据集使用虚拟化列表、表格和树：只实例化视口行加一行过扫描，
因此布局、绘制和行内存随视口而不是模型扩展。没有 GPU 驱动依赖，
没有 GL 上下文丢失，首帧没有着色器编译，也没有需要管理的纹理图集。
测量到的空闲循环占用不到单核的 0.3%，密集 1280x800 完整重绘约为 55-70 fps，
密集 4K 完整重绘在参考笔记本电脑上约需 38-48 ms，
而该尺寸下单个损坏行需要 3.3-4.1 ms。4K 数字是损坏驱动或静态内容的目标，
而不是持续动画的目标。空闲在真实合成器上也意味着空闲，而不只是在无头测试框架中：
自 0.10.0 起，获焦输入框不再以新的状态推送回应输入法的确认，
此前这会让一个无人触碰的窗口重绘，约占单核的 43%。
1.0 的实时守卫将获焦输入框的 5 秒切片保持在 1.5 秒 CPU 以下，
并在桌面注入输入时重试或跳过。

GTK 4 和 Qt Quick 是 GPU 优先的，在大规模变换、模糊、视频、3D 内容
和高分辨率持续动画方面会明显胜过 Pt。egui 也是 GPU 优先，但采用立即模式：
它每一帧都重建并重绘 UI，这非常适合工具和可视化，
但不太适合对电池敏感的桌面实用工具。LVGL 的软件渲染器针对小得多的显示器优化，
而且通常根本没有合成器。

### 4. 小型且有明确取向的控件集

Pt 提供盒/行/列容器、标签、按钮、输入框、组合框、文本区域、切换开关、
复选框、单选框、滑块、进度条、加载指示器、分段控件、滚动、换行、网格、
虚拟化列表、表格、树、标签页、侧边栏、图标、图标按钮、标签片、骨架屏、
分隔线、卡片和间隔件，以及原生弹出菜单、工具提示、仅选择组合框列表、
模态对话框和通知。设计语言由令牌驱动：色调化控件表面、柔和强调色按钮、
动画勾选标记和开关、焦点环，以及统一的深色/浅色调色板。
输入框和文本区域支持选择、剪切/复制/粘贴、按词选择/全选手势、撤销/重做
和拖出源。放置目标可以探查多 MIME 数据提供内容并异步流式读取已接受类型；
URI 列表文件拖动、拖动图像、滑动/捏合/长按手势、触控笔输入、惯性滚动，
以及具备减少动效感知的公开缓动，共同构成完整的交互层。
这足以用于实用工具窗口、设置面板、计数器、仪表盘、笔记工具、文件浏览器
和小型数据工具；它不是文档编辑器或电子表格工具包。GTK 和 Qt 拥有多年积累的
控件、对话框、完整模型/视图栈、菜单和平台集成。Slint 的组件集也在快速成长，
并拥有声明式语言；Pt 使用朴素的命令式构建方式，并配有流畅的绑定层。

1.0 的限制在 [README](../../README.zh-CN.md#limitations-in-10) 中如实列出：
对话框和通知留在窗口内，AT-SPI 暴露是可选的，流式放置数据以应用需要解码的
字节形式到达，拖动源需要活动的指针按压，触摸捏合/旋转由两个触点合成，
表格列保留应用设置的宽度并可隐藏，但应用仍拥有行顺序，
多列排序最多报告四个优先级而不重排模型，树节点保存纯文本，
行由 Pt 拥有，文本区域以样式化文本段编辑纯文本但没有双向布局。
触控笔工具、橡皮擦和笔杆按钮作为输入数据传递；绘制和手势语义仍由应用定义。
今天需要更多能力的项目应使用 GTK 或 Qt。

### 5. 许可与依赖形态

Pt 采用 Apache-2.0，包括绑定和示例。GTK 为 LGPL-2.1+；
Qt 视模块和用途为 LGPLv3/GPLv3 或商业许可；Slint 为 GPLv3 或商业许可。
Apache-2.0 对封闭产品中的静态链接友好，并带有明确的专利授权。
Pt 仍依赖系统字体和 Wayland 库，因此最终二进制并非无依赖，
但它们都不是 GUI 工具包或语言运行时。

egui 和 Nuklear 也采用宽松许可；如果 Rust 或立即模式很合适，它们是极佳选择。
LVGL 的 MIT 许可证非常适合嵌入式产品，但其架构面向裸机或 RTOS 显示器，
而不是 Wayland 桌面会话。

### 6. 没有运行时桥的绑定

- **GTK：** GObject Introspection 为多种语言生成绑定；运行时和类型系统都是 GObject。
- **Qt：** C++ 加 QML；Python 使用 PySide/PyQt。Java 并非官方提供。
- **Slint：** Rust 核心，从 `.slint` DSL 生成 C++/Python/JS API。
- **egui：** Rust 优先；非 Rust 使用由社区驱动。
- **LVGL/Nuklear：** C API 加社区绑定。

Pt 的 Python 和 Java 层没有生成的胶水代码、没有 JNI，也没有 GObject 运行时。
它们足够小，便于审计和调试；自 0.7 起，两者都封装了每个公共 C 函数——
1.0 时为 412 个——C++ 头文件也是如此；
参见 [bindings.md](bindings.md#binding-coverage)。

## 各工具包更合适的选择

- **选择 GTK 4**：用于完整的 GNOME 集成应用、无障碍、平台对话框、
  广泛控件和庞大的贡献者生态。
- **选择 Qt Quick**：用于 GPU 密集型、动画化、跨平台应用，
  或当 QML 和 Qt 商业支持适合团队时。
- **选择 Slint**：用于具有现代设计语言和桌面及嵌入式目标上 GPU 渲染器的
  声明式 Rust/C++ UI。
- **选择 egui**：用于开发者工具、调试器、可视化器和 Rust 项目，
  在这些场景中立即模式迭代比原生平台集成更重要。
- **选择 LVGL**：用于 RAM 紧张且没有桌面合成器的微控制器和嵌入式显示器。
- **选择 Nuklear**：用于极小的立即模式 UI，且渲染器已由你控制，例如游戏引擎。
- **选择 Pt**：用于以 C、C++、Python 或 Java 编写的小型 Linux/Wayland 原生
  实用工具，在这些项目中，Apache-2.0、扁平 ABI、一致的客户端标题栏、
  清晰文本和低空闲成本比庞大的控件目录或 GPU 特效更重要。

## Pt 在 1.0 中的位置

Pt 有意比成熟工具包更窄，但 1.0 冻结了一个可信的工作区外壳：
带稳定键选择的虚拟化表格和树、批量失效、多列排序和隐藏列，
与标签页、侧边栏、矢量图标和多行文本区域一起提供；
在 0.9 中，表格单元格变得可编辑，行获得了可选择范围，
列可以拖动到新顺序，树标签可以就地重命名。
在 0.10 中，同一套多行模型扩展到列表和树——范围与切换原语、Shift+单击、
Ctrl+单击、Shift+方向键，以及可从某一行或视口空白处开始并在每个视图中
选择其相交内容的橡皮筋框选——组合框也加入输入框之列，
既有下拉模式，也有随用户键入过滤自身列表的模式。
主题不再是全局开关：38 个语义颜色角色和 10 个几何度量
通过按窗口的覆盖表解析，因此应用可以像 GTK 和 Slint 重设单个节点那样
重设单个表面，标签片、骨架屏、忙碌和无效控件覆盖了设置面板或数据视图
实际显示的状态。放置目标可以探查多 MIME 数据提供内容并异步流式读取
已接受的类型，同时源可以一次提供多种类型，并获知目标执行了哪个动作；
标签和文本区域接受带逐段字体族和字号的样式化文本段；
表格和树响应真实的 AT-SPI `Table`、`TableCell` 和 `Selection` 接口。
在渲染器方面，合并式损坏索引与逐瓦片裁剪重绘、子树范围的布局失效、
平方距离圆角矩形路径和哈希字体面表取代了 0.7 记录为上限的四项成本；
守卫套件测量橡皮筋框选拖动、弹出层表面、4K 损坏帧和 100,000 行表格定位，
确定性快照测试框架则固定跨主题往返的绘制结果。
1.0 冻结移除了两个已弃用的拖动辅助函数，修复了启用 text-input-v3 时的直接输入，
并将无障碍桥扩展到只读标签和文本区域，同时不泄露密码字符。
它仍然是一个可工作的框架，拥有经过测试的渲染器、Wayland 集成、
四种语言的接口表面、可运行示例和可重现的性能数据。其主要风险是成熟度和范围，
而不是架构：C ABI 足够小，可以在兼容性策略下演进——
0.9 端到端运行了首次真实弃用周期，1.0 在策略中记录冻结，
并将检查清单转化为 `tools/release-check.sh`——渲染器、布局引擎、
数据视图和绑定分隔在接口之后，为双向文本段落布局、更丰富的文本模型
以及最终的 GPU 后端留出了空间。
